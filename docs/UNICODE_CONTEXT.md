# Opt-in Unicode context policy

`Policy.CONTEXTUAL` is an observation-oriented usability policy. It retains
every original-coordinate finding and all P2 caps, but allows selected
well-formed contexts that `balanced-v1` reviews. Its reports declare
`contextual-v1` and [schema v4](../schemas/inspection-v4.schema.json); the
default `balanced-v1` continues to emit [schema v3](../schemas/inspection-v3.schema.json)
with its existing decisions. The legacy `analyze()` path is unchanged.

The policy recognizes only these forms:

| Form | Recognition boundary | Malformed neighbor behavior |
|---|---|---|
| Emoji ZWJ and tag sequences | Exact RGI sequence in bundled Emoji 18.0 data, with no adjacent tag, joiner, or selector | Unrecognized ZWJ or tag remains review evidence |
| Arabic-block ZWNJ | Between two alphabetic U+0600–U+06FF characters | Repeated or displaced controls are not discounted |
| Devanagari ZWJ | U+094D VIRAMA, ZWJ, then a Devanagari letter | Other joiners remain review evidence |
| RTL isolate | One balanced RLI or FSI pair around simple RTL text, without nesting, line breaks, or embedded format controls | Unmatched, nested, LRI, or mixed-direction pairs remain review evidence |

Explicit U+202D/U+202E overrides still block even when other spans are
recognized. Mixed-script findings still prompt review. A recognized context
changes the *action* for that evidence; it never deletes evidence or rewrites
the candidate. The accepted forms are a blind spot for covert choices among
valid sequences. Recognized Unicode form does not prove benign intent, and
plain-text prompt injections remain out of scope.

The 30 project-authored development fixtures are pinned in
[`contextual-actions.json`](../evals/contextual-actions.json) and tested
literally. Under this policy, 0/17 project-labeled benign fixtures were held;
among nine constructed attacks, three were allowed, four reviewed, and two
blocked. All 16 selected clean samples in `test_false_positives.py` were
allowed. Five legitimate context constructions and six malformed/extra-carrier
near matches are paired in `test_unicode_context.py`; the near matches are
reviewed. These are selected examples, **not independent FP/FN estimates**.
The [context resource study](P3_CONTEXT_RESULTS.md) records local latency and
process peak observations for four one-megacharacter constructions.

## Data provenance and update process

The offline table includes 1,614 RGI ZWJ sequences and three RGI tag
sequences from the Unicode Emoji 18.0 data files. The pinned upstream copies
are under [`data/upstream/emoji18`](../data/upstream/emoji18); the packaged
derived table is [`emoji-context-18.0.txt`](../src/stegdetect/data/emoji-context-18.0.txt).
The [Unicode Emoji specification](https://www.unicode.org/reports/tr51/)
defines these RGI sets; [UAX #9](https://www.unicode.org/reports/tr9/) defines
directional isolates. This implementation recognizes a narrow subset of bidi
contexts; it is not a Unicode Bidirectional Algorithm implementation.

| Source | SHA-256 |

| [emoji-sequences.txt](https://www.unicode.org/Public/18.0.0/emoji/emoji-sequences.txt) | `1823dce71f3dd9cb0ad1976797baee4ffbdc1909756f43af8ce4c57f732843a4` |
| Derived table | `3c3d5f104f219c08c47333f80fc3d29364f5ff5ef536afd0c884aa0fb851b3fc` |

Run `python scripts/generate_emoji_context.py` to regenerate from the pinned
local upstream files. The script verifies both source hashes and the sequence
count; the test compares the generated bytes with the packaged file. Runtime
loads only the packaged file, checks its hash, and never downloads data.
Unicode data is distributed under the
[Unicode License v3](../src/stegdetect/data/UNICODE-LICENSE.txt), which is
included with the installed package. Update data, policy decisions, test
fixtures, measurements, and schema in a reviewed change, not by following a
mutable `latest` URL at runtime. The Python runtime's Unicode properties can
predate Emoji 18.0, so recognition does not assert identical rendering on
every runtime or platform.

No new carrier category was added. Variation selectors, interlinear
annotations, and deprecated formatting controls remain candidates. Each
needs its own generator, adversarial threshold, legitimate controls, and FP
measurement before a detection rule can ship.
